# План развития MD Card (ВКР)

**Рабочее название ВКР:** «Разработка системы генерации сайтов для малого бизнеса на основе предметно-ориентированного языка разметки с интеллектуальной поддержкой пользователя»

**История, которую рассказываем на защите:**
владелец малого бизнеса (барбершоп, репетитор, мастер маникюра, фотограф) описывает себя обычными словами → система генерирует сайт на предметном языке разметки, сама проверяет результат по схеме и исправляет ошибки модели → то, чего не хватает (нет телефона, цен), и ошибки, появившиеся при ручной правке, редактор подсвечивает и помогает исправить → готовый сайт публикуется в один клик, а клиент с него сразу звонит или пишет владельцу в мессенджер.

Источники ошибок, которые ловит валидатор: (1) ошибки нейросети — исправляются автоматически в цикле до показа пользователю; (2) нехватка данных — предупреждения, модель не должна выдумывать; (3) ошибки ручной правки — подсказки в редакторе.

Всё, что работает на эту историю, — делаем. Всё остальное — в «перспективы развития».

**Решение от 18.10.2026:** приём заявок (форма записи, база заявок, уведомления в Telegram) **не делаем**. Связь с бизнесом — через телефон и контакты в мессенджерах/соцсетях. Сайт остаётся полностью статическим.

Удалять их нельзя, пока не выгружен и не проверен код `get-site` (`npx supabase functions download get-site`) — скорее всего, он их читает.

**Заметки для ВКР**
- *Почему токен нельзя в `VITE_*`.* Vite подставляет все `VITE_*` переменные в JS-бандл как строки, поэтому токен Vercel видел любой посетитель через DevTools. Секрет должен жить там, где код выполняет сервер: в Edge Function, а браузер вызывает функцию от имени вошедшего пользователя.
- *Ключи в `deploy-vercel`.* Функция работает со встроенными `SUPABASE_URL` + `SUPABASE_ANON_KEY` и JWT пользователя, а **не** с service role. Это осознанно: функции нужно только убедиться, что сайт принадлежит пользователю (`auth.getUser()` + `sites.user_id = user.id`), а service role обходит RLS — права шире, чем нужно (принцип наименьших привилегий). Без проверки владельца любой вошедший пользователь мог бы публиковать произвольный HTML под нашим токеном Vercel.
- *Сигнатура `deployToVercel(html, siteId)` сохранена* — вызывающий код (`App.tsx`, `useSites.ts`) не менялся, изменение локализовано в одном модуле.
- *Тесты как фиксация поведения.* Тесты на парсер описывают текущее поведение, а не желаемое: это страховка перед рефакторингом этапа 2. Найденные странности помечены «текущее поведение» — это готовый список требований к новому валидатору (источник ошибок №3 — ручная правка):
  битый YAML даёт ту же ошибку, что и отсутствие `name`, без позиции; `accent: #abc` без кавычек — YAML-комментарий, цвет молча становится `auto`; при переводах строк CRLF не распознаются заголовки `##`; незакрытый `:::` поглощает все следующие секции; в блоках строка-продолжение, начинающаяся с латинского «слова:» (`Note: …`, `https://…`), становится новым полем и теряется; текст с `|` и строкой `---` считается таблицей; срезается отступ первой строки в `:::code`.
- *Проблемы.* `npm install` падал из-за файлов root в `~/.npm` (след старого `sudo npm`), установили с временным кэшем; `db pull` не выполнен без Docker; локально нет Deno, поэтому функция проверялась деплоем и ручной публикацией.

## Этап 2. Схема языка и валидатор — фундамент ✅ ВЫПОЛНЕН 18.10.2026

Главная «научная» часть реализации: язык описан формально, и **одна схема** используется в трёх местах — подсказки в редакторе, проверка ответов нейросети, системный промпт для нейросети.

**Структура модуля** `src/dsl/` (чистый TypeScript, без React — должен работать и в браузере, и в Deno):

```
src/dsl/
  schema/            # описание языка
    frontmatter.ts   # поля шапки: name, title, theme, business, phone, address, city, currency, contacts...
    blocks.ts        # блоки: cards, accordion, code, services, hours, map, reviews, contacts
    icons.ts
  parser.ts          # текст → AST с позициями (строка/колонка) у каждого узла
  validate.ts        # AST → Diagnostic[]
  rules/             # предметные правила, каждое — отдельный файл с тестами
  serialize.ts       # AST/JSON → Markdown (нужно для AI-режима «JSON по схеме»)
  prompt.ts          # генерация системного промпта для LLM из схемы
```

**Схема** — на Zod (v4 умеет `z.toJSONSchema()`, это пригодится для structured output). Для каждого блока: поля, обязательность, тип, допустимые значения, описание на русском (идёт в подсказки и в промпт), пример.

**Формат ошибки:**
```ts
interface Diagnostic {
  from: number; to: number          // позиция в тексте
  severity: 'error' | 'warning' | 'info'
  code: string                      // 'unknown-field', 'price-not-number', ...
  message: string                   // по-русски, понятное владельцу бизнеса
  fix?: { label: string; replace: string }   // автоисправление
}
```

**Правила валидации** (минимум):
- синтаксические: незакрытый `:::`, неизвестный блок, неизвестное поле, обязательное поле отсутствует;
- «возможно, вы имели в виду»: опечатки в именах тем, блоков, полей, иконок, соцсетей (расстояние Левенштейна);
- предметные — услуги и расписание: цена не число («1500р» → «1500», валюта в `currency`), время закрытия раньше открытия, дубли услуг, пустое описание у услуги, адрес без города;
- предметные — контакты:
  - нет ни одного способа связи (ни телефона, ни мессенджера) → предупреждение «клиенты не смогут с вами связаться»;
  - телефон не в российском формате → автоисправление к виду `+7 999 123-45-67`;
  - вместо имени пользователя вставлена ссылка (`https://t.me/ivan`) → автоисправление к `ivan`;
  - имя в Telegram не по правилам (5–32 символа, латиница, цифры, `_`);
  - WhatsApp указан не номером телефона;
  - `primary` ссылается на контакт, которого нет.

**Важно:** текущий `parseCardMarkdown` и рендер не ломаем — новый парсер выдаёт тот же `CardData`, старые тесты из этапа 0 должны проходить.

**Готово, когда:** на каждое правило есть тест, `validate()` возвращает диагностику с позициями, `prompt.ts` строит промпт из схемы.

**Решение автора (18.10.2026):** правила для услуг и расписания (цена не число, время закрытия раньше открытия, дубли и пустые описания услуг) переносятся в этап 3 — вместе с блоками `:::services` и `:::hours` (правило CLAUDE.md: новый блок делается целиком). В этапе 2 — схема существующих блоков и полей шапки (включая `business`, `phone`, `address`, `city`, `currency`, `contacts`), синтаксические правила, «возможно, вы имели в виду» и правила контактов.

Относительные импорты внутри `src/dsl/` пишутся с расширением `.ts` — этого требует Deno, а TypeScript фронтенда это разрешает (`allowImportingTsExtensions`).

- *Позиции.* Диагностика хранит смещения `from/to` в символах — это формат CodeMirror (этап 4). Строка/колонка для человека вычисляется из смещения (`offsetToLineCol`); строки делятся по `\n`, поэтому файлы с CRLF дают корректные номера строк.
- *Два слоя результата парсера.* AST хранит позиции каждого узла (шапка и её поля, секции, блоки `:::`, элементы, поля `key: value`, строки без ключа) — для валидатора и редактора. `CardData` строится из текста секций теми же функциями, что и раньше (перенесены в `src/dsl/sections.ts` без изменений). Так рефакторинг не меняет то, что видит пользователь, а все «странности» старого парсера становятся видны в AST и будут превращены в диагностику в шаге 5, а не исправлены молча.
- *Проверка совместимости.* Кроме 86 старых тестов, новый и старый парсер сравнивались на 20 000 случайно собранных документов (заголовки, блоки, незакрытые `:::`, CRLF, битый YAML) — результаты совпали полностью. Сравнение было разовым и в репозиторий не вошло: старого кода больше нет.
- *Ошибки YAML с позицией.* Шапка разбирается через `yaml.parseDocument`, а не `yaml.parse`: он не бросает исключение, а возвращает список ошибок с позициями и узлы с диапазонами в тексте.
- *Телефон в YAML.* `phone: +79991234567` YAML читает как число, и «+» теряется. Для новых полей бизнеса берётся исходный текст значения (`Scalar.source`), а не результат преобразования YAML.
- *Схема — единственный источник правды.* Темы, виды бизнеса, способы связи и иконки описаны один раз в `src/dsl/schema/` вместе с описанием по-русски и примером (`.meta({ description, examples })`). Из схемы их берут парсер, селектор темы и набор SVG-иконок. `Icons.tsx` типизирован как `Record<IconName, …>`: добавить иконку в схему и забыть нарисовать её нельзя — сборка упадёт.
- *Строгие объекты.* Все объекты схемы — `z.strictObject`: лишнее поле считается ошибкой. В JSON Schema это даёт `additionalProperties: false` — нейросеть в режиме «JSON по схеме» (этап 5) не сможет добавить выдуманные поля. `z.toJSONSchema()` переносит описания полей в JSON Schema, тесты это проверяют.
- *Схема описывает правильную форму, а не всё, что понимает парсер.* Парсер по-прежнему принимает, например, `accent: abc` без решётки или цвет из 8 знаков, но схема допускает только `#rgb`, `#rrggbb` и `auto`. Разницу между «понял» и «правильно» валидатор покажет как предупреждение с автоисправлением.
- *Цена.* Zod попал в бандл фронтенда: +83 КБ (+24 КБ в gzip). Это приемлемо, а при необходимости можно перейти на облегчённый `zod/mini` с тем же API схем.
- *Устройство валидатора.* `validate(text)` = парсер + список правил; правило — функция `(текст, AST) → Diagnostic[]`, по файлу на правило в `src/dsl/rules/`. Правила не знают друг о друге, поэтому новое правило добавляется одной строкой в список `RULES`. Результат отсортирован по позиции. Правила этапа 2:

  | Код | Что ловит | Важность | Автоисправление |
  |---|---|---|---|
  | `unclosed-frontmatter` | нет закрывающей `---` у шапки | ошибка | — |
  | `invalid-yaml` | синтаксис YAML: двоеточие в значении, Tab, повтор поля, кавычки | ошибка | кавычки вокруг значения; пробелы вместо Tab |
  | `missing-frontmatter`, `missing-name` | нет шапки / нет или пустое `name` | ошибка | вставить шапку / поле |
  | `missing-item-field` | у карточки нет `title`, у вопроса — `title` или `content` | внимание | — |
  | `unknown-field` | поле не из схемы: шапка, `contacts`, `links`, элементы блоков; «Note: …» и ссылка в начале строки-продолжения | внимание | присоединить к предыдущей строке |
  | `duplicate-field` | поле дважды в элементе (забыта пустая строка) | внимание | начать новый элемент |
  | `invalid-value` | тема, вид бизнеса, иконка, ссылка без https://, почта, `primary`, цвет | внимание | регистр темы; `https://` |
  | `accent-unquoted`, `accent-format` | `accent: #abc` без кавычек; необычная запись цвета | внимание | `"#aabbcc"` |
  | `unclosed-fence`, `nested-fence` | незакрытый `:::`; блок внутри блока | ошибка | вставить `:::` перед проглоченным заголовком |
  | `unknown-block` | `:::faq` и т.п. | ошибка | — |
  | `stray-text` | текст без поля в элементе блока | внимание | — |
  | `heading-no-space`, `crlf-heading` | `##Цены`; заголовок не распознан из-за CRLF | внимание | пробел; переводы строк во всём тексте |
  | `no-contacts` | нет ни телефона, ни мессенджера, ни почты (в т.ч. ссылок `tel:`, `t.me` в `links`) | внимание | — (контакты не придумываем) |
  | `phone-format` | телефон или WhatsApp не в виде `+7 999 123-45-67`; не похоже на российский номер | внимание | `+7 999 123-45-67` из `8-999-…`, `+7 (999)…`, `wa.me/…` |
  | `whatsapp-not-phone` | в WhatsApp не номер | внимание | — |
  | `contact-link` | ссылка или `@имя` вместо имени в Telegram, VK, Instagram | внимание | имя пользователя |
  | `telegram-username` | имя не по правилам Telegram | внимание | — |
  | `primary-unknown` | главная кнопка ведёт на неуказанный контакт | внимание | единственный указанный контакт |
  | `address-without-city` | адрес без города | внимание | — |

- *Важность.* «Ошибка» — сайт не построится или ломается структура (часть текста пропадает в чужом блоке). «Внимание» — сайт построится, но не так, как задумано (поле проигнорировано, цвет не применился).
- *Расширение формата `fix`.* В `DiagnosticFix` добавлены необязательные `from/to`: исправление не всегда меняет подчёркнутый текст. Например, ошибка «блок не закрыт» подчёркивает `:::accordion`, а `:::` вставляется ниже — перед проглоченным заголовком. Это совместимо с CodeMirror (этап 4), где действие исправления может менять любую часть документа.
- *Как проверяются исправления.* Тест каждого автоисправления применяет его (`applyFix`) и запускает валидатор снова: проблема с тем же кодом должна исчезнуть, а для структурных исправлений — `CardData` должен стать правильным (например, после закрытия блока «Контакты» снова отдельная секция). Тот же цикл «проверка → исправление → проверка» будет основой AI-генерации в этапе 5.
- *Странности старого парсера → диагностика.* Все странности из заметок этапа 0, кроме двух, теперь видны пользователю: битый YAML (с позицией и причиной), `accent: #abc`, CRLF в заголовках, незакрытый `:::`, «Note: …» и ссылка в продолжении. Не стали отдельными правилами: «текст с `|` и `---` считается таблицей» и «срезается отступ первой строки в `:::code`» — редкие случаи, оставлены на будущее.
- *Сообщения библиотеки YAML* — английские и технические («Flow sequence in block collection must be sufficiently indented…»). Валидатор переводит частые коды ошибок (`BLOCK_AS_IMPLICIT_KEY`, `TAB_AS_INDENT`, `DUPLICATE_KEY`, `MISSING_CHAR`, `MULTIPLE_DOCS`) в понятные сообщения и подчёркивает всю строку: позиция от библиотеки часто указывает на один символ, где разбор остановился.
- *Скрипт `npm run check:dsl`.* Node.js 24 запускает TypeScript без сборки (удаление типов), поэтому скрипт импортирует `src/dsl/` напрямую, без tsx. Пригодится для экспериментов этапа 7.
- *Опечатки: какое расстояние.* Используется расстояние Дамерау — Левенштейна (вариант OSA): кроме вставки, удаления и замены символа, перестановка двух соседних символов тоже стоит 1. Частая опечатка «titel» → «title» по обычному Левенштейну стоит 2 и в коротком слове не прошла бы порог.
- *Порог по длине слова:* до 2 символов — только точное совпадение (иначе `vk` «исправлялось» бы в любое двухбуквенное слово), 3–5 символов — 1 правка, длиннее — 2. Если два кандидата одинаково близки, подсказки нет: исправление в один клик не должно быть угадыванием.
- *Синонимы.* Владелец бизнеса пишет как привык: `телефон:`, `город:`, `tg:`, `ватсап:`, `primary: телеграм`. Расстоянием это не поймать, поэтому в схеме есть словари синонимов (`FRONTMATTER_ALIASES`, `CONTACT_ALIASES`, `BLOCK_ALIASES`). Синоним предлагается, только если он ведёт к допустимому в этом месте ключу: «телефон» внутри `contacts` не превращается в `phone`. Мессенджер, написанный в корне шапки (`telegram: ivan`), получает подсказку перенести его в `contacts`.
- *Подсказки встроены в существующие правила,* а не вынесены в отдельное: на одно неизвестное поле — одно сообщение, либо с подсказкой и исправлением, либо со списком допустимых полей.
- *Ограничение.* Поля внутри блоков пишутся латиницей: строка `Вопрос: …` в блоке — это текст, а не поле, поэтому русские названия полей блоков не распознаются.
- *Контакты — главное на сайте малого бизнеса,* поэтому правила о них самые подробные: сайт без способа связи не выполняет свою задачу. Владелец пишет контакты как привык: «8-999-123-45-67», «https://t.me/ivan», «@ivan», ссылку wa.me вместо номера. Валидатор приводит всё к одному виду, а ссылки сайт построит сам (этап 3) — владельцу не нужно знать их форматы.
- *Почему у некоторых правил нет автоисправления.* Исправление предлагается, только если правильный ответ однозначно следует из написанного: номер из 10 цифр, имя из ссылки, единственный указанный контакт для `primary`. Если для исправления нужны данные, которых нет (телефон, город, правильное имя в Telegram), валидатор только сообщает о проблеме. Подставлять что-то вместо владельца нельзя — то же правило «не выдумывать» будет у нейросети в этапе 5.
- *`@` в YAML.* `telegram: @ivan` — это не просто «неправильное имя»: в YAML значение не может начинаться с `@`, и вся шапка не разбирается. Для этой ошибки YAML (`BAD_SCALAR_START`) отдельное сообщение «Имя пользователя пишется без @» с исправлением.
- *Иностранные номера* (`+375 …`) не проверяются и не исправляются: правило рассчитано на российские номера, а ссылка для звонка построится как есть.
- *Сериализатор и «равенство».* Цель `serialize` — режим «JSON по схеме» (этап 5): нейросеть заполняет данные, а разметку строим мы. Поэтому разметка блоков строится из данных (`table`, `cards`, `accordion`, `code`), а не из исходного текста секции: у ответа нейросети его просто нет. Проверяемое свойство — `parse(serialize(card))` совпадает с `card` во всём, что видно на сайте (у блоков текст секции `content` не показывается), а повторная сериализация даёт тот же текст.
- *Кавычки в шапке* ставит библиотека `yaml` (`stringify`): она берёт в кавычки значения, которые иначе прочитались бы иначе — с двоеточием, `#`, `@`, номер из одних цифр. Ручного экранирования нет.
- *Чего язык не может выразить:* перевод строки в значении поля блока (парсер склеивает строки пробелом — сериализатор сразу пишет одной строкой) и секцию без названия не в начале (`##` без названия — это разделитель внутри предыдущей секции). Оба случая сериализатор сводит к ближайшему выразимому, а тесты это фиксируют.
- *Проверка на случайных документах:* 2000 документов из случайных строк (секции всех пяти видов, около 225 с данными блоков, незакрытые `:::`, «Note: …», таблицы без разделителя) проходят круговой путь. Тест детерминированный: генератор с фиксированным зерном.
- *Промпт из схемы.* `buildSystemPrompt()` обходит схему Zod и для каждого поля пишет описание, обязательность, допустимые значения и пример; для блоков — описание, поля элемента и пример разметки. Схема одна для промпта, валидатора и (в этапе 4) подсказок редактора: модель получает ровно тот язык, по которому её потом проверяют. Тесты проверяют, что в промпте есть каждое поле, контакт, тема, вид бизнеса, иконка и блок схемы; полный текст промпта лежит в снимке `src/dsl/__snapshots__/prompt.test.ts.snap` — его можно привести в приложении ВКР.
- *Два режима — основа эксперимента этапа 5/7.* `markdown`: синтаксис языка + справочник полей и блоков + пример документа. `json`: справочник полей + JSON Schema документа + пример JSON. Ответ в режиме json проверяется `documentSchema`, переводится `fromJson` в `CardData` и `serialize` — в разметку, которую затем проверяет тот же `validate()`. Пример документа и пример JSON описывают один и тот же сайт — это проверено тестом.
- *Правило «не выдумывать»* — первое в промпте: только факты из описания пользователя; нет данных — нет поля. Примеры помечены как вымышленные, чтобы модель не переносила из них телефон или адрес. Нарушение частично ловится валидатором (`no-contacts` — предупреждение, а не повод придумать номер), а число выдуманных фактов считается вручную в эксперименте 1.
- *Устаревшие поля* (`location`, `link` у карточек) помечены в схеме `deprecated: true`: парсер и валидатор их понимают, но нейросети они не предлагаются и в JSON Schema документа их нет.
- *Размер промпта:* около 6,2 тыс. символов в режиме markdown и около 12 тыс. в режиме json (JSON Schema с описаниями объёмная). Это важно для лимитов токенов GigaChat и будет одной из метрик эксперимента 1.
- *Проверка в среде Edge Functions.* Модули `prompt`, `validate`, `serialize`, `fromJson` запущены в Deno 2.9 с картой импортов `{"yaml": "npm:yaml@2", "zod": "npm:zod@4"}` и без `node_modules` проекта — так их увидит функция `generate-site`. Библиотеке `yaml` нужен доступ к переменным окружения (`LOG_TOKENS`); в Edge Functions он есть.
- *Проблемы.*
  - `npx` снова упал на файлах root в `~/.npm` (след этапа 0) — запускали с временным кэшем `npx --cache <папка>`.
  - Проверка на случайных документах нашла ошибку, которую не поймали тесты отдельных правил: для текста, начинающегося с пустой строки, диапазон первой строки получался перевёрнутым (`from > to`) — `lastIndexOf('\n', -1)` ищет с позиции 0. Исправлено в `lineAt`. Вывод для главы 3: тесты на конкретных примерах дополняются проверкой свойств («позиции всегда внутри текста») на большом числе случайных входов.
  - Генератор случайных документов поначалу давал слабое покрытие: у линейного конгруэнтного генератора младшие биты повторяются с коротким периодом, и соседние «случайные» решения оказывались связаны. Берём старшие биты (`seed >>> 16`). Кроме того, случайная шапка почти всегда содержала ошибку YAML (повтор ключа), а при ней правила шапки молчат — генератор теперь берёт каждый ключ один раз.
  - Deno-версия TypeScript строже вывела тип в одном месте (`Object.entries` у объединения схем) — уточнили тип явно. Проверку `npx deno check` стоит держать в привычке для всего кода `src/dsl/`.

**Заметки для ВКР (этап 3)**
- *Ссылки строит генератор, а не владелец.* Владелец пишет номер и имя пользователя как привык, `contactLinks()` превращает их в ссылки: `tel:+7…` открывает звонок, `https://t.me/<имя>` — Telegram, `https://wa.me/<цифры>` — WhatsApp. Одна функция используется блоком контактов, кнопкой «Записаться» (шаг 2), панелью связи (шаг 6) и разметкой Schema.org (шаг 7) — ссылки везде одинаковые. Если из значения ссылку построить нельзя, контакт показывается текстом, а валидатор объясняет, что исправить.
- *MAX.* Официальной документации о формате ссылки на профиль нет; по инструкциям пользователей личного имени пользователя в MAX нет, ссылка на профиль — `https://max.ru/u/<код>`, копируется в приложении (профиль → QR-код → «Поделиться»). Поэтому `contacts.max` — ссылка, а не имя, как у остальных мессенджеров; правило `max-not-link` подсказывает, где её взять. Описание поля в схеме и правило в промпте изменены соответственно.
- *Цена — число, валюта — в шапке.* В `price` пишется только число («1500», «от 1500», «1500–2000») или слово («бесплатно»); знак ₽ и пробелы в тысячах добавляет сайт (`formatPrice`: «1 500 ₽», неразрывные пробелы). Так цена остаётся данными: её можно сравнить, отсортировать и передать в Schema.org (`price` + `priceCurrency`, шаг 7). Самая частая ошибка владельцев и нейросети — «1500р», «1 500 ₽», «от 800 руб.» — исправляется автоматически (`normalizePrice`); если смысл неоднозначен («дорого»), валидатор только объясняет формат.
- *Часы — свой мини-язык внутри блока.* Поля блоков пишутся латиницей (`key: value`), а для часов это неудобно: владелец пишет «пн–пт: 10:00–20:00». Поэтому у `:::hours` нет полей — каждая строка разбирается отдельно (`parseHoursLine`): дни (короткие формы, полные названия по началу слова — «понедельник», «суббота», диапазоны, списки, «ежедневно», «будни») и время («10:00–20:00», «10-20», «с 9 до 21», «выходной», «круглосуточно»). Правило валидатора подсвечивает конкретную непонятную строку и говорит, что именно не понято — дни или время.
- *Одна функция статуса для превью и опубликованного сайта.* Бейдж «Открыто до 20:00» зависит от текущего времени, а сайт статический: HTML собирается один раз при публикации. Поэтому в экспорт добавлен единственный встроенный скрипт (только если есть блок часов). Чтобы не писать логику дважды, функция `hoursStatus` сделана самодостаточной (без импортов и внешних констант), и в скрипт вставляется её исходный код — `hoursStatus.toString()`. Тест проверяет, что этот код работает сам по себе; дополнительно проверено, что функция работает и после минификации в собранном `dist/`. Без JavaScript на сайте остаётся таблица часов.
- *Время посетителя, а не города бизнеса* — упрощение: статус считается по часам устройства посетителя. Для местного бизнеса посетители почти всегда в том же часовом поясе; учёт часового пояса города потребовал бы таблицы «город → пояс» — оставлено как ограничение.
- *Работа после полуночи* («пт: 22:00–02:00») поддержана в статусе, но валидатор всё равно предупреждает: для барбершопа или маникюра это почти всегда опечатка, а «10:00–8:00» автоматически предлагается исправить на «до 20:00».
- *Отзывы и «не выдумывать».* Отзывы — самый соблазнительный для нейросети материал для выдумки, а выдуманный отзыв на сайте реального бизнеса вводит клиентов в заблуждение. Поэтому: описание блока в схеме прямо говорит «только настоящие отзывы — придумывать их нельзя» (оно попадает в промпт), правило №1 промпта перечисляет отзывы среди запрещённого, а пример документа в промпте **намеренно не содержит** блока отзывов — образец с отзывами подталкивал бы модель добавлять их всегда. Проверяется в эксперименте 1 (число выдуманных фактов).
- *Оценка — число 1–5*, звёзды рисует сайт. Как и с ценой, частые записи («5/5», «★★★★☆», «9 из 10») исправляются автоматически, а неправильная оценка не показывается на сайте вовсе — лучше без звёзд, чем с неверными. Средняя оценка пригодится для `aggregateRating` в Schema.org (шаг 7).
- *Одна кнопка — один контакт.* «Записаться» у каждой услуги ведёт на `primaryLink()`: никакой формы и базы заявок (решение от 18.10.2026), клиент сразу попадает в звонок или чат. Без контактов кнопки нет — пустая кнопка хуже её отсутствия, а валидатор и так предупреждает `no-contacts`.
- *Блок без элементов.* `:::contacts` не повторяет данные, а показывает поля шапки: контакты указываются один раз и используются во всех местах сайта. В схеме у таких блоков вместо полей элемента — описание тела (`body`), оно же попадает в промпт.

**Готово, когда:** шаблон барбершопа отображается во всех темах, все кнопки контактов открывают правильные приложения на телефоне, экспортированный HTML проходит валидатор структурированных данных Schema.org.

## Этап 5. AI-генерация сайта с проверкой (1,5–2 недели)

**Edge Function `generate-site`** — цикл «генерация → проверка → исправление»:
```
промпт пользователя + системный промпт (из схемы, prompt.ts)
  → GigaChat → validate() → ошибки? → «исправь: <список>» → ... (максимум 3 итерации)
  → каждая попытка пишется в generation_logs
```
Модель не должна выдумывать контакты: если телефона или мессенджера нет в описании — поле остаётся пустым, валидатор выдаёт предупреждение.

**Два режима — это и есть эксперимент:**
- `mode: 'markdown'` — модель пишет разметку напрямую;
- `mode: 'json'` — модель заполняет JSON по JSON Schema из Zod, `serialize.ts` превращает его в Markdown.

Параметр `model`: GigaChat-2 / 2-Pro / 2-Max, а также GigaChat-3-Lightning / 3-Pro.

**Таблица `generation_logs`:** id, user_id, run_id, mode, model, prompt, attempt, output, diagnostics (jsonb), errors_count, tokens_in, tokens_out, latency_ms, created_at. С RLS: пользователь видит только свои записи.

**Лимиты:** не больше N генераций на пользователя в сутки (считаем по `generation_logs`). У физлица в GigaChat один поток — при одновременных запросах показывать «в очереди».

**UI:** кнопка «Создать сайт по описанию» → поле ввода + выбор ниши → результат открывается в редакторе. Кнопка «Объяснить и исправить» у ошибки в панели «Проблемы» (функция `fix-block`: на вход фрагмент + диагностика).

**Готово, когда:** из описания в 2–3 предложения получается валидный сайт, все попытки видны в `generation_logs`.

## Этап 6. AI-подсказки при наборе (1 неделя)

Человек пишет «таблица цен: мужская 1500, детская 900» → серым текстом появляется готовый блок → **Tab** принять, **Esc** отклонить.

1. **Уровень 1, без нейросети:** `detectIntent(line)` по ключевым словам (цены, услуги, часы, адрес, контакты, телефон, телеграм, вопросы, отзывы…) → сразу предлагается пустой шаблон блока в автодополнении.
2. **Уровень 2, GigaChat:** если в строке есть данные — по паузе ~1 с или `Ctrl+Space` вызывается функция `complete-block` (короткий промпт + контекст: frontmatter и соседние блоки).
3. Ответ показывается только после `validate()` без ошибок (иначе одна итерация исправления).
4. Устаревшие запросы отменяются (`AbortController`).
5. Серый текст — виджет-декорация CodeMirror + обработчик Tab/Esc.
6. События (показана / принята / отклонена, задержка) → `editor_events`.

**Готово, когда:** подсказка появляется за 1–3 с, принимается одним нажатием, в логах считается доля принятых.

## Как работать с Claude Code

1. `PLAN.md` и `CLAUDE.md` лежат в корне репозитория. `CLAUDE.md` Claude Code читает автоматически в каждой сессии.
2. **Один этап — одна сессия.** Запустить `claude`, включить режим планирования (Shift+Tab), написать: «Прочитай PLAN.md, этап N. Изучи текущий код и предложи план». Посмотреть план, поправить, потом разрешить делать.
3. Большие этапы дробить: «этап 3, только блок services» → проверить → коммит → следующий блок.
4. После каждого этапа — проверить руками (`npm run dev`), коммит, отметка в PLAN.md, `/clear` перед следующим этапом.
5. Пункты «Готово, когда…» — это критерии приёмки. Можно прямо просить Claude Code проверить их в конце.

**Пример стартового запроса для этапа 0:**
> Прочитай PLAN.md и выполни этап 0. Начни с удаления временных файлов и настройки Vitest с тестами на текущий src/lib/parser.ts. Перенос деплоя на Vercel в Edge Function сделай отдельным коммитом. Перед изменениями покажи план.

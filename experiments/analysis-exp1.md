### Валидность: сразу → после автоисправлений → после исправления моделью

Каскад по первой попытке (n = 48 в каждой строке):
- **сразу** — ответ модели в 1-й попытке без ошибок, до обработки;
- **+ автоисправления** — ошибки 1-й попытки убрала обработка (autofix);
- **+ исправление моделью** — валидным стал только ответ на запрос исправления (2-я попытка и далее);
- **не валиден** — итог с ошибками.

| Модель | Режим | Сразу | + автоиспр. | + исправл. моделью | Итого валидных | Не валиден |
|---|---|---|---|---|---|---|
| 2-Pro | markdown | 48 | 0 | 0 | **48 (100 %)** | 0 |
| 2-Pro | json | 43 | 0 | 4 | 47 (97,9 %) | 1 |
| 2-Max | markdown | 48 | 0 | 0 | **48 (100 %)** | 0 |
| 2-Max | json | 45 | 0 | 3 | **48 (100 %)** | 0 |
| 3-Lightning | markdown | **23** | 25 | 0 | **48 (100 %)** | 0 |
| 3-Lightning | json | 41 | 0 | 0 | 41 (85,4 %) | 7 |
| 3-Pro | markdown | 39 | 9 | 0 | **48 (100 %)** | 0 |
| 3-Pro | json | 45 | 0 | 0 | 45 (93,8 %) | 3 |
| 3-Ultra | markdown | 48 | 0 | 0 | **48 (100 %)** | 0 |

Наблюдения:
1. **Markdown: 240 из 240 валидны уже после первой попытки.** Запрос исправления у модели не понадобился ни разу.
   Вся разница между моделями — в том, сколько работы взяла на себя обработка.
2. **Ошибки, которые убирает автоисправление, — почти только «незакрытая шапка».** В ответах моделей 1-й попытки
   (markdown): `unclosed-frontmatter` у Lightning — 24 из 48, у 3-Pro — 9 из 48, ещё одна `invalid-yaml` у Lightning.
   У 2-Pro, 2-Max и Ultra ответы без ошибок. Без автоисправления у Lightning в markdown было бы 48 % валидных, а не 100 %.
3. **JSON: автоисправление не помогает ничем** (+0 во всех строках). Ошибки JSON — синтаксис и схема — оно не чинит,
   их чинит только модель. Модели GigaChat-2 и Ultra это делают. Lightning и 3-Pro повторяют ту же ошибку, и запуск
   останавливается на 2-й попытке с исходом `no-progress`.
4. **Режим против модели.** У 2-Pro, 2-Max и Ultra с первой попытки JSON чуть хуже markdown (90–96 % против 100 %).
   У Lightning (85 % против 48 %) и 3-Pro (94 % против 81 %) — наоборот: сам ответ модели лучше в JSON. Но в markdown
   эти ошибки исправимы автоматически, в JSON — нет. Итог по режимам: markdown 100 %, JSON 95,4 %.

**Поправка к колонке `rescued_by_autofix_share` в metrics.csv.** Она считается по *итоговой* попытке. У Lightning
markdown там 0,354, а по каскаду автоисправление спасло 25 из 48 = 0,521 первых попыток. Расхождение даёт проход по
предупреждениям (п. «Попытки» ниже): после него итоговой становится 2-я попытка, и её ответ уже без ошибок. Для главы 3
использовать каскад. Предложение — добавить его колонки в export-logs (обработку это не затрагивает).

|---|---|---|---|
| 2-Pro | 1,17 | 8 | 1,10 |

В markdown все вторые попытки — это проход по предупреждениям («Желательно исправить»), а не исправление ошибок
(`generate.ts`: если ошибок нет, но есть исправимые предупреждения, — одна дополнительная попытка). Поэтому среднее
число попыток здесь меряет «аккуратность» ответа, а не его валидность.

### Невалидные итоги (11 из 480, все — json, все `no-progress` на 2-й попытке)

| Причина | Запуски | Чья проблема |
|---|---|---|
| `currency: Invalid input: expected "RUB"` — валюта из описания (BYN, KZT, USD) | Lightning: t06, n09, p08; 3-Pro: t06, n09 | **схема**, см. ниже |
| у блоков `services`/`hours` нет `items`/`lines` — пустые разделы на скудных описаниях | Lightning: t04, n05, p09 (`minimal-input`) | модель |
| `business: "yoga"` вне перечня ниш (вместо `other`) | Lightning: o05 | модель |
| ссылка `links[0]` без `url` («Звоните» + icon phone) | 3-Pro: t10 | модель |
| JSON с комментарием `// укажите реальный номер` после телефона-заглушки | 2-Pro: t05 (обе попытки) | модель |

Попутно для разметки: у Lightning в o05 раздел «О нас» — это дословно текст-заглушка из промпта («Текст о бизнесе
своими словами — из описания.»).

**Валюта — главная находка повтора.** Схема шапки допускает только `currency: RUB`
(`src/dsl/schema/frontmatter.ts:144`, `z.enum(['RUB'])`), и в JSON-режиме это проверяется схемой. Markdown-валидатор
перечень не проверяет, а grounding (`ground.ts`) оставляет другую валюту, если она названа в описании. В трёх описаниях
с иностранной валютой (t06 — 25 BYN, n09 — 8000 тенге, p08 — 1200 USD; 30 запусков) получилось так:

| Что вышло | Запусков |
|---|---|
| валиден, валюта верная (Lightning md: BYN, KZT; 2-Pro md: USD) | 3 |
| валиден, валюта не в шапке, а в тексте цены (3-Pro json p08: «1200 USD») | 1 |
| **валиден, но цены показаны в рублях** (`currency: RUB` или без валюты → ₽) | **21** |
| не валиден, потому что модель честно перенесла валюту (Lightning json ×3, 3-Pro json ×2) | 5 |

Отсюда:
- **7 из 9 «исправлений моделью» в JSON** (2-Pro t06, n09; 2-Max t06, n09, p08; Ultra t06, p08) — это замена
  верной валюты на рубли ради прохождения схемы. Формально запуск стал валидным, по смыслу — испортился
  (8000 тенге → 8000 ₽).
- 5 из 11 невалидных итогов — штраф за правильный ответ.
- Автоматическая валидность здесь отбирает не ту сторону. Это нужно учесть в выводах о JSON-режиме
  и показать ручной разметкой: из трёх описаний в пакете разметки есть только t06.
- Обработка заморожена на `edc3f00780a2`, поэтому до конца эксперимента схему не меняем. Для главы 3 это ограничение
  валидности и кандидат в доработки: валюта списком (RUB, BYN, KZT, USD, …), а не одна RUB.

### Предварительные выводы (до ручной разметки)

1. По автоматической валидности markdown + обработка — 100 % у всех пяти моделей. JSON — 85–100 %. Разница между
   режимами создана в основном автоисправлением (оно есть только для markdown) и схемой валюты, а не моделями.
2. Сильнее всего от обработки зависят Lightning и 3-Pro: их ответы до обработки — 48 % и 81 % валидных в markdown.
   GigaChat-2 и Ultra дают валидный markdown сами.
3. Ultra — лучшее сочетание по автоматическим метрикам: 100 % в обоих режимах, сама почти не ошибается, быстрая, краткая.
   Но кэш промпта у неё не работает.
4. Валидность не равна правильности: валюта показывает, что «исправление» ради схемы может искажать факты. Вывод о
   качестве — только после разметки (выдумки, вводящие в заблуждение, ложные удаления, ловушки).
5. Согласованность повторов (`repeat_*`) пока пустая — посчитается после повторов 2 и 3.

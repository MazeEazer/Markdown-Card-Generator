### Выводы (до ручной разметки)

1. **Режим.** Markdown + обработка дают 100 % валидных у всех пяти моделей в обоих повторах. JSON — 95,6 % по всем
   описаниям и 97,6 % без иностранной валюты. Разницу создают автоисправление (есть только для markdown) и схема
   валюты, а не модели.
2. **Вклад обработки.** Сильнее всего от неё зависят Lightning (сырой markdown валиден в 45 % случаев) и 3-Pro (83 %).
   GigaChat-2 и Ultra пишут валидный markdown сами. В json автоисправление ничего не добавляет: ошибки синтаксиса
   и схемы чинит только модель, а Lightning и 3-Pro этого не умеют (`no-progress`).
3. **Модель.** По автоматическим метрикам лучшая — Ultra: 100 % в обоих режимах, почти без ошибок, самая быстрая
   (медиана 3,1–3,8 с) и краткая. Кэш промпта у неё не работает: весь вход оплачивается полностью. Lightning быстрая,
   но в json даёт 85 % валидных, а в markdown держится на автоисправлениях. 2-Max — самая медленная.
4. **Валидность не равна правильности.** 13 из 17 «исправлений моделью» в json — это подмена валюты. Выводы
   о качестве содержания — только после ручной разметки.
5. **Повторяемость.** Итог валидности — свойство пары «модель × описание», он воспроизводится. Конкретный текст
   сайта — нет.

## Находки ручной разметки (порция 1: b02, b06, b09, t03)

1. **Проверка по описанию не чистит контакты в свободном тексте.** По наблюдению на этом примере, проверка по описанию сверяет поля шапки и контактов, но не текст разделов (код `ground.ts` для этой записи не перечитывался). В b06 (GigaChat-3-Lightning, markdown) в ответе FAQ дошло до сайта «по телефону +7 900 000-00-00 (если есть)»: номера в описании нет, поле `phone` пустое, поэтому обработка ничего не нашла. По правилу 5 это выдумка, которая дошла, и ошибка, вводящая в заблуждение: клиент позвонит на несуществующий номер.
2. **Проверка по описанию удаляет настоящий английский адрес.** В b09 описание на английском («Bauman st. 22»), модель пишет по-русски («ул. Баумана, 22», «Бауманская ул., 22»); значение не совпадает с описанием, и автоисправление `ungrounded-contact` убирает адрес. Это ложное удаление на 7 из 10 сайтов b09: 2-Max (md, json), 3-Lightning json, 3-Pro (md, json), 3-Ultra (md, json); адрес сохранили только 2-Pro (md, json) и 3-Lightning md — у 3-Pro json адрес остался только в блоке карты, у 3-Lightning json — в title и тексте. Следом уходит блок карты (`map-no-address`), и адреса на сайте нет совсем у 2-Max md и json и у 3-Pro md. Причина: сверка адреса не учитывает перевод и транслитерацию. Пока обработка заморожена, это ограничение эксперимента; для главы 3 — пример ограничения проверки «по подстроке».
3. Пустой accordion в JSON-ответах Lightning и 3-Pro: обработка его убирает (`empty-block`), но модель его всё равно создаёт — по правилу 3 это нарушение правил, а не «дошло».

## Ограничения

1. **Два повтора вместо трёх** (отступление от исходного плана, решение 20.10 после анализа повторов 1–2). Разброс
   оценивается по одной паре повторов на условие. Согласованность — доля совпадений из двух, без оценки дисперсии
   по трём и более. Решение принято после просмотра данных, поэтому указываем его как отступление.
2. **Повторы в один вечер, подряд** (17:12–19:19 UTC). Повторяемость измерена в пределах одного вечера. Меняется ли
   поведение GigaChat между днями (сборки, нагрузка), эксперимент не показывает. Порядок моделей уравновешен
   (прямой + обратный), поэтому дрейф внутри вечера на сравнение моделей не влияет. Пример такого дрейфа —
   ускорение 2-Max в повторе 2.
3. **Схема валюты.** `currency` допускает только RUB (`src/dsl/schema/frontmatter.ts`). На трёх описаниях из 48
   json-режим штрафует правильный ответ, а «исправление» искажает факт. Обработка заморожена, схему не меняли. Итоги
   приведены с этими описаниями и без них, в разметке — отдельная пометка `misleading_schema`.
4. **Выборка составлена Claude** (`author:claude`), а не реальными владельцами бизнеса. На тег приходится 3–5 описаний,
   поэтому сравнение по тегам описательное, без проверки значимости.
5. **Ручная разметка — по одному повтору** (повтор 1, 16 описаний). Тексты повторов заметно различаются, поэтому
   разметка описывает типичный, но не единственный ответ. Повторяемость содержания не измерялась.
6. **Технические сбои** перезапускаются (правило протокола). Это корректно для сравнения качества моделей, но
   доступность сервиса GigaChat в итоговые доли не входит — она приведена отдельно (1 сбой на 961 обращение).
7. **Одна температура (0,2) и один набор параметров**, без вариантов промпта. Выводы относятся к этой настройке.

**Валюта — главная находка повтора.** Схема шапки допускает только `currency: RUB`
(`src/dsl/schema/frontmatter.ts:144`, `z.enum(['RUB'])`), и в JSON-режиме это проверяется схемой. Markdown-валидатор
перечень не проверяет, а grounding (`ground.ts`) оставляет другую валюту, если она названа в описании. В трёх описаниях
с иностранной валютой (t06 — 25 BYN, n09 — 8000 тенге, p08 — 1200 USD; 30 запусков) получилось так:

| Что вышло | Запусков |
|---|---|
| валиден, валюта верная (Lightning md: BYN, KZT; 2-Pro md: USD) | 3 |
| валиден, валюта не в шапке, а в тексте цены (3-Pro json p08: «1200 USD») | 1 |
| **валиден, но цены показаны в рублях** (`currency: RUB` или без валюты → ₽) | **21** |
| не валиден, потому что модель честно перенесла валюту (Lightning json ×3, 3-Pro json ×2) | 5 |

Отсюда:
- **7 из 9 «исправлений моделью» в JSON** (2-Pro t06, n09; 2-Max t06, n09, p08; Ultra t06, p08) — это замена
  верной валюты на рубли ради прохождения схемы. Формально запуск стал валидным, по смыслу — испортился
  (8000 тенге → 8000 ₽).
- 5 из 11 невалидных итогов — штраф за правильный ответ.
- Автоматическая валидность здесь отбирает не ту сторону. Это нужно учесть в выводах о JSON-режиме
  и показать ручной разметкой: из трёх описаний в пакете разметки есть только t06.
- **Методика разметки** (PLAN.md, протокол эксперимента 1; README пакета `annotation/`): если в описании другая валюта,
  а цены в ₽, это «ошибка, вводящая в заблуждение, вызвана схемой». Она считается в `misleading` и отдельно в колонке
  `misleading_schema`, в `details` — с пометкой «схема». Так ошибки схемы не смешиваются с ошибками модели.
- Обработка заморожена на `edc3f00780a2`, поэтому до конца эксперимента схему не меняем. Для главы 3 это ограничение
  валидности и кандидат в доработки: валюта списком (RUB, BYN, KZT, USD, …), а не одна RUB.

### Находки ручной разметки, порция 3 (кандидаты в доработки)

1. **Проверка цен не понимает «к» (тысяча).** В p02 описание «свадьба от 25к», модель правильно пишет «от 25000», а `ungrounded-number` не находит число 25000 в описании и удаляет цену. Во всех 10 запусках по p02 это ложное удаление настоящей цены: свадьба остаётся без цены. Системный дефект обработки; кандидат в доработки: приводить «25к», «25 тыс.», «25 000» к числу до сверки.
2. **Проверка по описанию подтверждает число, если оно есть где угодно в описании,** без привязки к услуге. Поэтому цена 6000, которая в описании p01 относится к часу в студии, проходит проверку и у «Семейная фотосессия» и «Детская фотосессия» (GigaChat-2-Max, markdown): две выдуманные цены дошли до сайта. Кандидат в доработки: сверять число с услугой, рядом с которой оно стоит в описании (или хотя бы предупреждать о цене, одинаковой у нескольких услуг).
3. **Нормализация телефона могла бы исправлять «+8» → «+7» вместо удаления.** В p05 (GigaChat-3-Lightning, json) модель написала «+8 4852 33-90-17», цифры из описания («8 4852 33-90-17»), но с неверным префиксом; `ungrounded-contact` удалил номер, и на сайте нет телефона. Это неточный перенос модели и верное удаление неверного значения, но контакт потерян. Кандидат в доработки: `phone-format` приводит российский «8…» и «+8…» к «+7…».
